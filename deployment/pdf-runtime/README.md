# Single-container PDF runtime

On the own-engine branch, this directory packages NuaForma's Java 25 application and a separate bounded Java 17 PDF validator. DOCX layout and PDF writing execute in the hosting JVM; LibreOffice is neither installed nor used as a fallback. The `qualification` target invokes only the validator, while `service` packages the actual REST entry point. This new candidate is under qualification and requires a fresh distribution audit. Published containers remain unchanged. See the [native input profile](../../nuaforma-docx-pdf/README.md) and [on-premise service guide](SERVICE.md).

## Build and application use

Unreleased issue #93 source adds a strict default-on operator conformance policy; see [service configuration](SERVICE.md#docx-pdf-and-fonts) and [embedded configuration](../../nuaforma-docx-pdf/README.md#operator-conformance-policy-unreleased-issue-93-source). Explicit `false` skips only per-document veraPDF, never PDFBox, probe/runtime identity, network denial, private JVM/files or budgets. All validators remain bundled with the same license/source/SBOM obligations. Enabled validation still binds the requested profile to the final file digest and fails closed. Disabled output carries an export profile, not a verified-conformance claim; the operator owns downstream checking. Default-on release qualification remains mandatory. Published alpha images and digests stay immutable.

Build with JDK 17 and JDK 25 installed and the repository wrapper, then Docker with BuildKit. The library/validator toolchain remains 17; the separately packaged server uses 25:

```sh
./gradlew :nuaforma-docx-pdf:preparePdfValidation :nuaforma-docx-pdf:prepareVeraPdfValidation
python3 tools/container/prepare_verapdf_materials.py nuaforma-docx-pdf/build/verapdf-validation
docker build --platform linux/amd64 --file deployment/pdf-runtime/Dockerfile \
  --build-context pdfvalidation=nuaforma-docx-pdf/build/pdf-validation \
  --build-context verapdfvalidation=nuaforma-docx-pdf/build/verapdf-validation \
  --target qualification --tag nuaforma-pdf-runtime-qualification:11-pinned deployment/pdf-runtime
```

The named validator contexts contain only staged validator distributions and retained license/source/profile materials, never the checkout, private fonts, local instructions or secrets. The service accepts only Gradle's production `installDist` directory as its application context. Its entry point captures immutable fonts from `/usr/share/fonts` and operator mounts, checks application/JVM/validator SHA-256 inventories, and configures `nuaforma.pdf.validator.launcher=/opt/nuaforma/bin/validate-pdf`. The old renderer-launcher property no longer selects a backend. Embedded consumers can configure `NativePdfConfiguration` and `PdfProcessValidator` directly.

Runtime execution requires Docker's `--init` (or an equivalent platform-provided child reaper), UID/GID 1000, a read-only outer root, `--cap-drop ALL`, `--security-opt no-new-privileges`, the adjacent absolute-path `seccomp.json`, `--pids-limit 128`, `--memory 2g`, `--cpus 2` and a writable `/tmp` tmpfs capped at 512 MiB with mode 1777. Do not run the Java application alone as container PID 1: terminated conversion children can otherwise remain as orphaned zombie registrations after cancellation. Docker supplies its init helper; NuaForma does not bundle another init dependency. Mount only the application's explicitly needed inputs and output destinations. Never mount a Docker socket. These are qualification settings, not permission to disable host protections.

The profile retains Moby's default-deny container filter but permits the reviewed AMD64/ARM64 user-namespace setup and mount operations required by Bubblewrap. The operations remain subject to kernel user-namespace capabilities; the container receives no host `SYS_ADMIN`. Inside the namespace, `renderer-seccomp.c` denies mount/namespace reconfiguration, network socket families other than AF_UNIX, ptrace and other privileged interfaces. Normal process/thread creation remains available. This is not `seccomp=unconfined` or a privileged container.

Bubblewrap exposes a minimal immutable validator root, private `/dev` and `/tmp`, and read-only access to the current request directory. It retains private user/PID/network/IPC/UTS/mount namespaces, clears inherited environment data, and provides no procfs or LibreOffice compatibility mounts. Only validation runs here; native rendering uses bounded request-local state in the application JVM. Validation has fixed arguments and CPU/file/address-space limits. Isolation failure leaves PDF unavailable, without an unsandboxed validation fallback. The historical `/opt/nuaforma/renderer` path and inventory filename now contain only the minimal validator OS and remain for tooling compatibility.

The source native path is exercised by the registered-provider and REST integration tests, `renderNativeDocxProof`, and the service/policy/container tools. Keep all existing DOCX/Word PDF sources and approved golden images unchanged. Candidate PDFs and new Word exports belong in fresh evidence directories. ### Headless device boundary

The development launcher no longer uses Bubblewrap's `--dev`, which also mounts `devpts`. It creates a private tmpfs at `/dev`, a private `/dev/shm` directory, and individually binds only the standard character devices `/dev/null`, `/dev/zero`, `/dev/full`, `/dev/random` and `/dev/urandom`. There is no `/dev/pts`, `/dev/ptmx`, `/dev/tty`, host device-directory bind or interactive-terminal requirement. Conversion, font enumeration and both PDF validators use this same boundary. The existing namespaces, OCI masks, seccomp policies, capability restrictions and resource limits remain unchanged; failure still makes PDF unavailable. This source change does not modify previously published images.

`python3 -m unittest discover -s tools/container -p 'test_*.py'` verifies that the synthetic probe uses the exact production device arguments. The real sandbox probe additionally checks device identities and usability, private shared-memory storage and absent terminal paths. Native runtime qualification is still required on each target architecture and host security policy; absence of a SELinux audit record is not proof that SELinux permits a mount. Do not disable SELinux, AppArmor or seccomp to work around setup failures.

`./gradlew :nuaforma-docx-pdf:test :nuaforma-server:test` exercises the PDF library on Java 17 and server/provider/architecture integration on Java 25. `prepareRuntimeQualification` in the PDF module and `prepareEngineQualification` in server stage explicit test-only main programs without test libraries in their executable classpath. Run PDF-module qualification on Java 17; the server's staged test entry points require Java 25. Do not treat these test entry points or read-only qualification mounts as final service/container packaging.

`RuntimeQualification <fixture-root> <fresh-copy-directory> copy-matrix` runs the production conversion-copy implementation over the fourteen synthetic fixtures. The copies are then converted and structurally validated with the actual bundled runtime using `tools/pdf-evaluation/qualify_runtime.ps1 -SourceDirectory <copies> -Destination <fresh-run> -Mode convert`. `verify_production_copies.py` independently compares structure and unaffected binary parts to the approved research copies; it normalizes only three known generated diagnostic shape labels, not IDs, text, fonts or geometry. Source hashes must remain unchanged.

Stage/rasterize with `stage_runtime_review.py`, inspect metadata/fonts and scan barcodes with `inspect_results.py`, compare Word coordinates with `assess_geometry.py`, and inspect every unique full-page raster using `review_pages.py`. `scan_highdpi.py --backend libreoffice` separately decodes complete pages at 300 DPI. Use the approved decoder and bundled PDF tooling; keep all outputs, private fonts and binaries ignored. The production-copy matrix has fourteen PDFs, 44 pages, unchanged pagination/sizes, all embedded fixture fonts and four Code 39 `NF001` scans at both 100 and 300 DPI. Its 44 page rasters match the earlier qualified Linux matrix pixel-for-pixel. Modern inline text-box drift remains scoped to [issue #32](https://github.com/NuaForma/NuaForma/issues/32); arbitrary-template equivalence is not claimed.

For real core-to-provider execution, `PdfEngineQualification <docx-fixture-root> <private-font-directory> <fresh-output-directory>` tests classpath discovery, PDF selection, two concurrent tenant-specific barcode documents, dynamic multi-section watermarks, print/preview-only and template-private font embedding, cancellation while the actual LibreOffice conversion process is running, resource stream closing and private temporary cleanup in the same container. `stage_engine_review.py` independently rasterizes and inspects the five resulting PDFs (12 pages), checks tenant references/font embedding and decodes four rotated barcodes. It compares all five watermark pages pixel-for-pixel with the visually reviewed reference because LibreOffice exports VML watermark text as vector outlines rather than extractable PDF text. This must be run separately from the prepared-copy matrix, because converting prepared copies does not test template evaluation or core orchestration.

`dev.nuaforma.server.adapters.ktor.PdfRestQualification <docx-fixture-root> <private-font-directory> <fresh-output-directory>` additionally exercises actual loopback HTTP within this same container: multipart templates/fonts, two distinct tenant barcode documents and a five-page dynamic watermark. Use the same mandatory isolation flags, read-only staged application/fixture/font mounts and a dedicated output mount; no port publication or network access is needed. `stage_engine_review.py --fixtures tenant-a tenant-b watermark-dynamic --compare-all-pages` compares all nine raster pages and page counts with the reviewed embedded run, inspects embedded fonts and independently decodes both rotated references. Private fonts remain test-request inputs, not runtime-image contents. The shipped service entry point is independently exercised by `tools/container/qualify_service.py`, including actual-conversion shutdown and missing-converter behavior; see [the service guide](SERVICE.md#qualification-and-release-preparation).

`sandbox_probe.c` and `run_sandbox_probe.sh` are independent qualification tools, not renderer features. Compile the C probe statically in the Bubblewrap build stage and place it with a synthetic `visible.txt` in a private request directory. Mount synthetic `secret.txt` files outside that directory at `/app` and `/other` and set only `SYNTHETIC_TENANT_SECRET=synthetic-only`. The probe verifies those outer mounts/env values are invisible inside, network sockets and namespace/mount changes are denied, private AF_UNIX works, the root is read-only, UID is non-root, limits apply and the inner filter remains active. No real secrets or customer documents are used.
