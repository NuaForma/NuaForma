# Native AMD64 and ARM64 containers

The source service and separate development Playground target Linux AMD64 and ARM64. Java 25 runs the application and Java 17 runs each independent bounded PDF validator. The container contains neither LibreOffice nor Bubblewrap and needs no custom seccomp/AppArmor files. See [runtime defaults](APPARMOR.md), [service configuration](SERVICE.md) and [Java compatibility](../../docs/java-runtime-compatibility.md).

Stage inputs with both JDKs and the repository wrapper, using the [build instructions](README.md#build-and-run). Select the desired native platform through `NUAFORMA_PLATFORM=linux/arm64` or `linux/amd64` when using Compose. The Dockerfile pins multi-architecture Debian and Temurin indexes and checks the selected Debian architecture. Library bytecode remains Java 17 on both platforms.

Qualification must run on the matching native Linux architecture. An emulated build may help compilation checks but does not establish runtime qualification. The native workflow builds production and Playground candidates, keeps default runtime security policies and exercises real HTTP generation, independent PDF/PDF-A validation, JVM identities, font/extension mounts, concurrent operations, cancellation, cleanup and SBOM bytes. It uploads no image and publishes no release.

Retain init, UID/GID 1000, read-only root, dropped capabilities, no-new-privileges and the reviewed resource bounds. No additional user/mount/PID namespace setup is performed inside the application container. Docker Desktop, Podman, rootless engines and OpenShift retain their normal engine/platform requirements; support claims require measured evidence for the actual runtime/version. Published images and their version-specific deployment kits remain unchanged until a matching release is authorized.
