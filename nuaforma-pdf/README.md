# Shared PDF engine: alpha foundation

`nuaforma-pdf` is a Java-17-compatible, experimental source library for the own-engine track. It converts a bounded, format-neutral document model to standard PDF 1.7 or independently validated PDF/A-1b, 2b and 3b using the already reviewed PDFBox 3.0.8 dependency. The default remains single-page; opt-in exact-line pagination now supports fixed tables and shared page bands in the [report proof](../tools/pdf-evaluation/own-engine/REPORT.md). It requires no Word, LibreOffice, HTTP service, filesystem font installation or commercial license.

The registered `nuaforma-docx-pdf` provider and source server/container use this shared engine. Its production DOCX reader translates qualified [letter](../tools/pdf-evaluation/own-engine/README.md), [report](../tools/pdf-evaluation/own-engine/REPORT.md), [table](../tools/pdf-evaluation/own-engine/ADVANCED.md) and [anchored-image](../tools/pdf-evaluation/own-engine/ANCHORED_IMAGES.md) profiles into the neutral model. Rendering runs in the hosting JVM, while independent output validation uses a bounded Java 17 child. There is no LibreOffice fallback. ODT remains planned. See the [provider guide](../nuaforma-docx-pdf/README.md) for source limits; the native version is not yet published.

## Minimal Java API

The [note profile](../tools/pdf-evaluation/own-engine/NOTES.md) adds immutable `PdfNote` definitions, owning `PdfNoteCall` occurrences, definition-local labels and physical separator policies. Footnotes reserve page-bottom space and continue without repeating their labels; endnotes follow the main text. Source adapters resolve display numbers before pagination. `PdfTextStyle.baselineShift` expresses physical glyph rise independently of DOCX or ODT. Notes retain logical identities and working PDF backlinks; this does not create PDF tags or add level A output profiles. See the qualification record for source limits and the known Word continuation-boundary difference.

Text may carry `PdfTextNavigation` independently of styling: `PdfLink.External` creates inert HTTP/HTTPS/mailto links, `PdfLink.Internal` refers to a unique `PdfDestination`, and an optional destination title creates a flat PDF outline entry. Final physical placements determine clickable rectangles and targets. See the [navigation profile and Word comparisons](../tools/pdf-evaluation/own-engine/NAVIGATION.md) for limits, including unsupported bidi/frame navigation and the bounded single-underline style.

```java
var style = new PdfTextStyle("regular", 11);
var paragraph = new PdfParagraph(List.of(new PdfTextRun("café €", style)));
var document = new PdfDocument(
    new PdfPage(595.28f, 841.89f, new PdfMargins(56.7f, 56.7f, 56.7f, 56.7f)),
    List.of(paragraph));
byte[] result = new PdfEngine().render(document,
    List.of(new PdfFont("regular", callerSuppliedTrueTypeBytes)));
```

Coordinates and sizes are points (1/72 inch); content flows from the top-left inside the margins. Font IDs explicitly select real regular/bold/italic font files; there is no synthetic bold/italic or system-font fallback. Resource byte arrays and collections are copied. The engine owns per-call PDF state and returns bytes only after successful layout, writing, font finalization and required conformance validation. The caller owns its input/output files. Failure does not publish a partial result to a caller stream.

The model includes page/margins, paragraphs with inline text/image items and before/after spacing, RGB text colors and PNG images with explicit physical dimensions. `PdfParagraphFormat` adds left/center/right alignment, physical left/right/first-line indentation, optional exact line height and collapsed paragraph spacing. Exact lines currently use an experimental 80% baseline; this does not reproduce all Word line policies. It is independent of DOCX/ODT/parser/PDFBox types. Other page policies, styles, units and semantic roles in the [full design](../docs/architecture/conversion-engine.md) remain planned rather than empty placeholder APIs.

## Alpha output profiles and font embedding

`render(document, fonts)` retains standard PDF 1.7. Select another profile explicitly through `PdfOutputOptions`; there is no silent downgrade.

| Profile | PDF version | Transparent PNG | Delivery check |
|---|---|---|---|
| `STANDARD` | 1.7 | Supported | Existing structural/resource checks |
| `PDFA_1B` | 1.4 | Rejected, including an alpha channel or indexed transparency | Independent explicit PDF/A-1b validation |
| `PDFA_2B` | 1.7 | Supported | Independent explicit PDF/A-2b validation |
| `PDFA_3B` | 1.7 | Supported | Independent explicit PDF/A-3b validation |

Archival output embeds the runtime's built-in sRGB ICC profile, an output intent and matching XMP/Info metadata. Optional bounded title/author values are XML escaped. PDF/A-1b disables object-stream compression. No profile adds attachments, interactive forms, encryption, signatures or accessibility tags. PDF/A-3b support does not imply attachment support or PDF/UA compliance.

All fonts are caller-supplied TrueType resources with checked embedding permissions. `PdfFontEmbedding.SUBSET` remains the default. `new PdfFont(id, bytes, PdfFontEmbedding.FULL)` embeds the complete original font program; this permits a font's no-subsetting flag, while restricted/bitmap-only permissions still reject. Full embedding costs more output bytes and retains the same resource/output limits. There is no font substitution.

Configure the trusted host's independent validator when selecting PDF/A:

```java
var validator = new PdfProcessValidator(java17Executable, validatorJarPaths, privateTemporaryRoot);
byte[] archival = new PdfEngine(validator).render(document, fonts,
    new PdfOutputOptions(PdfOutputProfile.PDFA_2B, "Report", "NuaForma"));
```

`PdfProcessValidator` runs the already reviewed veraPDF 1.30.3 components in a separate Java 17 JVM. They are absent from the renderer host's runtime dependencies. The child checks the requested flavour and hashes the unchanged file; the parent requires its exact SHA-256 receipt and unchanged bytes. Archival output without a validator fails as `VALIDATION_UNAVAILABLE`; failed, missing, timed-out or mismatched validation fails as `VALIDATION_FAILED`. An injected `PdfConformanceValidator` is trusted host configuration and must implement the same independent exact-byte policy; never accept it from a document/request. A caller-supplied validator must support concurrent calls when its engine is shared; the supplied process validator is verified with concurrent requests. A callback modifying the bytes is rejected. There is no archival validation opt-out in this source API.

Validation uses a private per-call directory, a 256 MiB JVM heap, 64 MiB direct-memory limit, 16 KiB captured-output limit and a default 30-second timeout (maximum 120 seconds). Interruption kills/reaps the child and retains the caller interrupt flag; input files are removed. This is a bounded child-process boundary, not a fully qualified hosted OS sandbox or aggregate concurrency/memory guarantee. A shared validator can be used concurrently; the registered provider adds bounded admission and hosting deadline/cancellation checks.

`./gradlew :nuaforma-pdf:prepareOwnEngineValidation` stages the ignored local validator runtime under `nuaforma-pdf/build/pdfa-validation`, with existing upstream license notices. It does not publish a runtime, dependency or release. The renderer artifact remains Apache-2.0; upstream validator components retain their reviewed licenses. Distributing an alpha still requires the existing candidate-specific license/notices/source audit and production integration. No commercial dependency or new published module is introduced.

The [profile evaluation workflow](../tools/pdf-evaluation/own-engine/README.md#alpha-output-profile-qualification) records real validation, complete font streams, concurrency, rejection/cleanup checks and pixel equality against the standard-PDF path. The existing Word proofs remain the independent layout references.

## Paragraph-bound images

`PdfParagraph.anchoredImages` snapshots up to eight `PdfAnchoredImage` resources. Physical x coordinates are page-relative; y coordinates are relative to either the containing paragraph or its page. Paragraph-bound images move with a new-page anchor paragraph. Foreground placement, explicit distances, top/bottom and left/right/largest/both-sided rectangular exclusions retain text flow across paragraphs and pages. `PdfImageCrop` removes fractions from the source edges and clips the stretched result to the image's declared width/height. Source parsing remains in `nuaforma-docx-pdf`; the model contains no DOCX-specific types.

Wrapped keep groups, lists/tabs/inline objects, RTL image wrapping, overlapping floating image layers, tables intersecting active exclusions, page-band/cell anchors, tight/through wrapping, behind-text placement, arbitrary image rotation/flips and alternate fill rectangles are not qualified and reject. An unbreakable word wider than its available region also rejects. Source and physical-page budgets still apply. See the [Word trials and regression coverage](../tools/pdf-evaluation/own-engine/ANCHORED_IMAGES.md).

## Physical page sequences

`PdfDocument(List<PdfPageSequence>, maxPages)` accepts resolved content ranges with their own `PdfPage`, optional `PdfFlow` and `PdfPageNumbering` policy. Each range starts on a fresh page and retains physical dimensions/margins. Numbering continues unless an explicit start is supplied. Global page/text/block/paragraph/tab/image/leader budgets span all ranges. Collections are defensive snapshots. Existing `PdfDocument(page, blocks, flow)` overloads retain their behavior; `page`, `blocks` and `flow` remain first-range views. See the [mixed-size trial](../tools/pdf-evaluation/own-engine/SECTIONS.md). Continuous/explicit odd/even/column source section transitions remain unsupported.

`PdfFlow.firstPageBands` and `evenPageBands` accept resolved `PdfPageBands(header, footer)` pairs. Null retains the shared bands; an explicit empty pair suppresses them. First-page selection applies to each sequence's first content page and wins over even-page selection. Parity follows displayed page numbers, including restarts. All variant resources join document budgets. The [page-band trial](../tools/pdf-evaluation/own-engine/PAGE_MASTERS.md) covers the default continuous-numbering profile; the [numbering trial](../tools/pdf-evaluation/own-engine/NUMBERING.md) adds explicit starts, continuation and optional padding. Bands must fit reserved margins.

`PdfPageNumbering(start, alignParity)` accepts starts 0–9999; null continues the preceding range. Actual displayed values must remain within 0–9999. Optional parity alignment inserts one blank before a restart when its parity differs from the preceding range's next number. That blank uses the new range's geometry, has no bands, counts toward the physical document/page budget and is excluded from sequence totals. There is no leading padding before the first range. The format adapter decides whether to enable this policy; no DOCX/ODT types enter the shared model.

`PdfTableCell.verticalAlignment` defaults to TOP and accepts CENTER/BOTTOM over naturally measured row heights, including horizontal/vertical spans and atomic nested tables. Page-band field resolution retains the policy. A non-TOP cell must fit wholly within one physical page slice; fragmented rows or merged cells crossing pages reject explicitly. The [cell-alignment trials](../tools/pdf-evaluation/own-engine/CELL_ALIGNMENT.md) document source rules and qualified combinations. Fixed column widths remain the default. Optional [natural content widths](../tools/pdf-evaluation/own-engine/NATURAL_WIDTHS.md) measure direct text cells before pagination; general AutoFit redistribution and preferred/percentage dimensions remain unqualified. Uniform table borders retain their existing qualified combinations. The [solid cell-border qualification](../tools/pdf-evaluation/own-engine/CELL_BORDERS.md) adds per-side solid strokes/removal with one resolved style per source table. The [table-combination proof](../tools/pdf-evaluation/own-engine/BORDER_COMBINATIONS.md) additionally covers spans, one nested level, whole-row pagination and Letter. The [row-fragment proof](../tools/pdf-evaluation/own-engine/BORDER_FRAGMENTATION.md) extends this to explicitly splittable TOP-aligned rows with horizontal spans on A4 and Letter. Conflicting styles and oversized non-splitting custom-border rows remain unqualified.

## Page fields

`PdfPageNumber(style)`, `PdfPageCount(style)` and `PdfSequencePageCount(style)` implement typed decimal `PdfPageField` controls in reserved bands, including band-table cells. They resolve to the displayed page number, physical document total and current range's content-page count respectively. The writer finishes body pagination and optional padding before resolving and measuring bands. Single-page ranges without flow also contribute. Actual values must fit fixed reserved areas; overflow rejects rather than growing margins, changing the body or emitting guessed totals. Resolution occurs before output bytes are returned and remains request-local.

PAGE controls reserve four UTF-16 units in the aggregate text budget; document/sequence totals reserve two under the 32-physical-page maximum. These existing per-page controls belong in page bands. Symbolic body fields use the separate reference types below. Formatted/Roman page values, general expressions and PDF viewer page labels remain unsupported. The [global field proof](../tools/pdf-evaluation/own-engine/FIELDS.md) and [sequence-numbering proof](../tools/pdf-evaluation/own-engine/NUMBERING.md) record source profiles, boundary/concurrency checks and remaining limits.

## Contents, captions and cross-references

`PdfSequenceField` retains decimal counters, explicit restart/repeat and optional heading-level resets. `PdfReferenceField` represents text/page references and current/global/sequence page counts; `PdfReferenceTarget` snapshots actual bookmarked runs instead of a cached field value. `PdfContents` expands a blank marker paragraph into styled heading entries with optional internal links and leaders. Heading list labels and resolved sequence values participate in the generated titles. Page references use the destination's displayed number, including section restarts. Fields resolve before layout and repeat pagination to a stable result, bounded to eight passes. Missing targets, cycles, excessive expansion and unqualified repeated current-page fields reject explicitly.

`PdfBlockSemantics` and `PdfSpanSemantics` preserve logical roles, levels, known caption associations and stable identities through field iteration and final text fragmentation. The logical hierarchy retains references and reading order independently from paint coordinates, preparing later PDF/A-1a/2a/3a output and the future ODT adapter. This increment emits no PDF structure tree and makes no level-A or PDF/UA claim. [Qualification and current limits](../tools/pdf-evaluation/own-engine/REFERENCES.md).

## Lists and numbering

`PdfNumbering.resolve` is a pure batch resolver over immutable `PdfListDefinition`/`PdfListLevel` rules and source-ordered `PdfListStep` values. Each call owns its counters. Independent instances can use separate sequences or share a `sequenceId`, with explicit restarts. Decimal/leading-zero, repeated Latin letters (A…Z, AA, BB…), Roman and bullet formats, ancestor placeholders and legal decimal labels are bounded. Latin letter formats intentionally follow Word's repeated-letter sequence, not spreadsheet column names. Unsupported formats, missing ancestors and counter/label budgets fail explicitly.

Readers attach a resolved `PdfListLabel` to each paragraph. Its text remains separate from `runs`, with list identity, level and ordinal retained for later semantic output. The renderer measures/embeds its actual font, aligns the label left/center/right, implements tab/space/no suffix and uses a declared default tab interval when a wide label overruns its explicit tab. Body continuation indentation is independent of label position. Labels paint only on the first line, so pagination/relayout cannot advance counters or repeat a label. `PdfParagraphFormat.outlineLevel` preserves heading level; this does not itself generate PDF tags or bookmarks.

The [eight-page Word trial](../tools/pdf-evaluation/own-engine/LISTS.md) qualifies body lists, three levels, start overrides, continued sequences, chapter-style inheritance, label styling and hanging/first-line indentation. The test DOCX reader rejects source lists in tables/frames/bands, full level overrides, linked numbering styles and unqualified combinations. Arbitrary scripts and production DOCX/ODT integration remain later work. The neutral types and pure resolver remain inside this one shared artifact, ready for a future ODT reader; no new package artifact or dependency is added.

## Tabs and leaders

`PdfTab` carries a typed inline tab with an actual font style. `PdfTabSettings` provides immutable physical left/right/center/decimal stops, an explicit decimal separator and default interval. Real mixed-font advances determine alignment; dots, hyphens and underscores fill measured gaps as decorative PDF artifacts. Left-tab fields can wrap; other aligned fields must fit the current line. Whole-paragraph alignment must be left; overlapping or overflowing fields fail explicitly. See the [two-page Word trial](../tools/pdf-evaluation/own-engine/TABS.md) for source inheritance, limits, accepted wrapping differences and evidence. These types remain in this one shared artifact.

## Automatic spacing and resolved source styles

`PdfAutomaticLineSpacing` selects a 1–10 multiple of the supplied TrueType font's natural `hhea` line box and preserves its ascent/descent/gap. Extra spacing follows each line. Exact spacing and the original single-page default retain their previous behavior; explicit exact and automatic policies cannot be combined. Flow, table and frame measurement share the same box calculation. The current automatic profile accepts runs with identical natural line metrics (including the qualified bold/italic faces), rejecting mixed sizes/metrics or inline images instead of silently fitting them to an inaccurate common box.

The [two-page style proof](../tools/pdf-evaluation/own-engine/STYLES.md) qualifies source defaults, paragraph/character/table-style inheritance, direct overrides, Latin theme font references, single/1.5/double spacing and suppression between equal contextual paragraph styles. Source-specific inheritance resolves in the test adapter; the shared model receives effective fonts, styles and physical paragraph spacing. No DOCX theme/style nodes enter shared layout. Complex default-toggle combinations, conditional table styles, source automatic-before/after flags, line-count paragraph units and general font matching remain outside that proof profile. The production DOCX reader resolves this qualified style profile.

## International text and language

The [first international proof](../tools/pdf-evaluation/own-engine/INTERNATIONAL.md) qualifies Russian, Ukrainian and Greek text in paragraphs, fixed tables and numbered lists, using existing supplied Liberation Sans faces. `PdfTextStyle.languageTag` retains a bounded ASCII language tag (2–8 initial letters, optional 1–8 alphanumeric subtags, at most 64 characters); it is emitted as marked-content `/Lang` metadata and does not select a replacement font. The test DOCX reader resolves `w:lang/@val` through existing style precedence. This prepares the same neutral model for future ODT `xml:lang` input without source-format types in layout.

Precomposed Greek/Cyrillic source text uses the same measured cmap advances, embedded subsets and Unicode output as the qualified Latin route. The separate [bounded Hebrew proof](../tools/pdf-evaluation/own-engine/HEBREW.md) adds explicit `PdfParagraphFormat.textDirection = RIGHT_TO_LEFT` for unpointed Hebrew with numbers, wrapping, font faces, fixed cells and page bands. Direction is independent of physical alignment; the null default retains the original route. Mixed Hebrew/strong-LTR paragraphs, Hebrew with LEFT_TO_RIGHT direction, combining marks, mirrored RTL punctuation, RTL lists/first-line indentation, bidi tabs/inline images, Arabic and other unqualified scripts reject explicitly. Step 5 remains in progress; mixed directions and complex shaping are not qualified. The [page format matrix](../tools/pdf-evaluation/own-engine/PAGE_FORMATS.md) qualifies A4/A3/US Letter/Legal in portrait and landscape with Latin, Greek and Cyrillic report text; the [mixed-size proof](../tools/pdf-evaluation/own-engine/SECTIONS.md) adds next-page policy transitions.

## Supported and rejected behavior

- Tested horizontal Latin, Greek and Cyrillic text, precomposed accents, common punctuation and euro sign. Unsupported scripts, combining marks, control/format characters and unpaired surrogates fail explicitly. This is not general Unicode shaping.
- Greedy wrapping on ordinary spaces, preserving words across run/font changes. Line-edge whitespace is not a preserved formatting mechanism; use paragraph indentation instead. Long unbreakable words or single-page overflow fail with `CONTENT_OVERFLOW`; flow pagination is an explicit opt-in, without shrinking or hidden fallback.
- The same supplied font's cmap advances determine measurement and output. Typed PDF operators write those exact encoded glyphs, avoiding an unmeasured second GSUB/ligature transformation. `ToUnicode` and real font subsets preserve extraction. This deliberately unshaped qualified-script path must not be advertised for complex scripts.
- Standalone TrueType outlines only, with a bounded, valid table directory and OS/2 embedding-permissions table. Restricted, malformed/reserved low permission flags and bitmap-only fonts reject. Fonts prohibiting subsets require explicitly selected full embedding, as described above. CFF/collections remain unsupported. A technical embedding flag does not replace the caller's font license rights.
- PNG only: bounded encoded bytes, signature/header checks and decoded-dimension limits before PDFBox image decoding. No external resource retrieval.
- Opt-in `PdfFlow`: exact-line or qualified automatic-line paragraph pagination, fixed-width `PdfTable` cells with uniform padding/borders and explicit fills, repeated leading headers and shared `PdfPageBand` header/footer content. Bands reserve margin space, and `PdfPageNumber` resolves only inside bands. Overlapping bands and page-budget overflow fail explicitly. Omitting `PdfFlow` retains single-page overflow behavior.
- Body-flow paragraph rules: `keepWithNext` protects a following paragraph's widow-safe start, `keepLines` keeps a whole paragraph together, `widowControl` prevents single first/last lines, and `pageBreakBefore` overrides a previous keep without creating an initial blank page. Style inheritance and explicit false overrides are resolved by the test reader; neutral flags default off, whereas Word's implicit widow-control default is on. A keep chain must fit its protected minimum on a fresh page; impossible groups/kept paragraphs reject rather than silently relax. Keeps may target the first atomic table row or a whole image, but split-row targets and wrapped-frame combinations reject. Keeps in table cells and page breaks inside frames/bands reject. See the [ten-page Word proof](../tools/pdf-evaluation/own-engine/PAGINATION.md) and [ordered roadmap](../docs/architecture/own-engine-roadmap.md).
- The [advanced table trials](../tools/pdf-evaluation/own-engine/ADVANCED.md) add validated `columnSpan`/`rowSpan`, one nested table level and line-boundary row fragments. `PdfTableCell.blocks` accepts paragraphs/tables; its `paragraphs` view contains direct paragraphs only. Nested borders may consume parent right padding but cannot leave the parent cell. Row splitting (`allowSplit`) is opt-in; an atomic row moves whole when it fits a fresh page. An oversized atomic row still rejects unless `splitOversized` explicitly permits content-preserving fragmentation. This differs deliberately from Word's clipping behavior for an oversized `cantSplit` row. There is no production fallback/option change.
- The [page-band and text-frame trials](../tools/pdf-evaluation/own-engine/FRAMES.md) verify images in both bands, fixed-size `PdfTextBox` blocks with physical page/flow-cursor anchors, padding, fill/border, paragraph alignment, vertical alignment and clockwise center rotation. Frame text remains actual embedded-font PDF text. The qualified source subset uses unrotated rectangular VML frames and page-relative DrawingML frames. Rotated PNG Code 39 barcodes are independently scanned on full pages; barcode fonts are not qualified by this image-based trial.
- `PdfBoxWrap.NONE` reserves no body space. Unrotated `TOP_BOTTOM` frames use forward-only exclusion areas in `PdfFlow`: text uses space above the frame, skips intersecting line boxes, and continues below. Combined wrapped frames/body tables, retroactive page-relative exclusions, frame splitting/autofitting, arbitrary square/tight wrapping, nested frames, legacy VML rotation/text-flow combinations and floating frames inside tables/bands are unsupported. Frame content exceeding its line-box area or rotated physical page bounds fails explicitly without clipping or shrinking. Paragraph anchoring here means the block's current flow cursor; general source anchor relocation/overlap reconciliation across page breaks remains future work.
- Combined vertical spans/nesting with allowed row splitting are rejected in this profile. Fragmentation of oversized rows in a vertically merged table is also rejected. Nested tables remain atomic inside their parent cell. General field expressions, arbitrary line-break controls, ODT import, PDF/A level A, PDF/UA and PDF/X remain unsupported. Qualified DOCX, navigation, page-master, cell-alignment and pagination behavior is described in the profiles above.

`PdfRenderException.code` distinguishes invalid resources, unsupported text, missing fonts/glyphs, embedding restrictions, overflow, resource limits and interruption. Invalid API arguments use `IllegalArgumentException`. No source text or font bytes appear in diagnostics. Interruption is cooperative and retains the caller's interrupt flag; it is not a hard process deadline.

Engine limits: one page by default or at most 32 opt-in flow pages, 1,000 main blocks, 2,000 paragraphs including cells/bands, 500 rows and 16 columns per table, 128 blocks per cell and one nested table level, 1,000 runs per paragraph, 100,000 UTF-16 text units total, 16 distinct fonts (8 MiB each/32 MiB total), PNG 4 MiB each/16 MiB total and at most 8,192 pixels per dimension/16 megapixels each, output 16 MiB. `PdfRenderControl` adds per-call cancellation, stricter output and cumulative decoded-image budgets. These are defensive bounds, **not** a measured hosted-service memory guarantee. Native integration uses request-local state and bounded admission; aggregate memory/concurrency/deadline qualification remains necessary. Only independent validation uses a child process; see the [execution decision](../docs/architecture/conversion-engine.md#9-execution-resources-and-capacity).

Frames accept 1–128 paragraphs each and participate in the existing aggregate text/image/paragraph budgets. Geometry must be finite and bounded; rotated extents include the border. Render/layout/PDFBox state is owned by each `render` call. A shared stateless `PdfEngine` and immutable models/font/image snapshots can be used concurrently; the frame regression shares one engine across 12 requests on four threads and verifies distinct text and decoded image pixels without cross-request contamination. This is correctness verification, not a throughput or hosted-isolation guarantee.

## Reproduce and verify the letter

Engine-only visual baselines and their strict replacement policy are documented in the [golden-image guide](src/test/resources/visual-goldens/README.md). Candidate generation does not overwrite references. Tests compare all twenty-six pages of seventeen neutral-model fixtures with the published Image Comparison 5.0.0 Kotlin DSL, using exact pixel equality alongside inventory/content/geometry/font checks. Failure diagnostics retain the actual PDF and expected/actual/difference images; the library is a test-only dependency and adds no production runtime or Playground behavior.

```sh
./gradlew :nuaforma-pdf:test
./gradlew :nuaforma-pdf:renderFoundationLetter
```

The second command writes `nuaforma-pdf/build/foundation/foundation-letter.pdf` using the test-only licensed fonts and the approved project logo. It is a synthetic Dutch letter containing accents, euro, real bold/italic and a searchable `office affinity` case. The build output is ignored; font licenses/provenance remain in [test resources](src/test/resources/fonts/README.md). Production library JARs do not bundle these fixture fonts; the source container separately provisions its reviewed font package.

Tests reopen the actual bytes, extract Unicode, inspect embedded subsets/ToUnicode, font faces, page/image geometry and text bounds, and reject overflow, unsupported shaping, missing glyphs, restricted fonts, malformed images and oversized decoded images. Concurrent renders and Java callers are exercised. Render the generated PDF with an independent viewer for visual QA; text assertions alone do not prove appearance. See the [architecture](../ARCHITECTURE.md#own-pdf-engine-development-track) for the full roadmap and integration boundary.

Changes are developed on a work branch targeting `feature/own-pdf-engine`. Keep the worktree until authorized delivery/merge, then remove it after preserving any needed ignored QA artifacts. This milestone does not authorize publication or switching the live converter.

## Requested page watermarks

The additive `PdfEngine.render(document, fonts, options, control, watermark)` overload accepts an immutable format-neutral `PdfWatermark`; the existing render signatures remain available. It draws centered background text on every physical page without altering body/table/note layout. The selected supplied font retains embedding-permission checks and Unicode mapping. Text, font identity, RGB color, opacity and clockwise rotation are explicit; cumulative text/output/cancellation limits apply. Logical Unicode is retained as `ActualText`; rotated text extraction can otherwise reflect physical glyph order. Latin, Greek, Cyrillic and the existing bounded Hebrew/number policy are supported; mixed Hebrew/LTR, Arabic/complex shaping and unsupported controls fail explicitly.

Requested watermarks work with standard PDF, PDF/A-2b and PDF/A-3b. PDF/A-1b rejects **all** requested watermarks, including fully opaque decoration; no transparency downgrade or raster flattening occurs. DOCX adapters resolve expressions before creating the neutral decoration. Plain shared-model callers supply already resolved single-line text.

## Rich-text source feature

The selected alpha.5 release adds immutable single strikeout through `PdfTextStyle.withStrikethrough`. The writer uses OpenType OS/2 metrics. Original six-property Java/Kotlin constructor/copy/destructuring descriptors remain executable; value methods are explicit and Kotlin reflection no longer reports a data class. See [the compatibility and qualification guide](../docs/rich-text.md). The RTF parser stays outside this neutral library.
