# Early DOCX to PDF backend evaluation

> **Historical renderer comparison.** Subsequent production work implemented the approved isolated LibreOffice backend, conversion-copy compatibility, watermarks, fonts and standard/PDF/A B-profile output. Statements below about unimplemented providers, unbuilt containers, pending checks or untested archival profiles describe their respective experiment stages. For current capabilities and qualification limits, see the [PDF provider guide](../nuaforma-docx-pdf/README.md) and [service container guide](../deployment/pdf-runtime/SERVICE.md). Original measurements remain unchanged.

Research for issue #10, begun 2026-10-11. LibreOffice was selected for production implementation on 2026-10-12; no production PDF provider is implemented yet. The comparison is reproducible through [the separate research tooling](../tools/pdf-evaluation/README.md), which does not change NuaForma's dependencies, published artifacts or engine contracts.

## Decision status

The unchanged renderers do not satisfy the complete early-product fidelity requirements. LibreOffice is the stronger candidate for requested watermarks; its initial rotated VML barcode defect is addressed for the measured profile by the private-copy experiments below. docx4j/FOP embeds the barcode font and produces a scanable barcode, but loses its rotation and the requested watermarks. Adopting either unchanged would silently weaken agreed behavior.

The user approved investigating a bounded LibreOffice-specific conversion compatibility layer for the rotated VML text box, applied only to an intermediate copy and never to the returned DOCX. The conversion-copy experiments below restore barcode scanability but do not yet establish acceptable geometry. This is research approval, not adoption of a production renderer or a passing fidelity certification. Do not replace barcode text with an image, change the DOCX template profile or silently drop unsupported content without a separate decision.

On 2026-10-12 the user explicitly accepted the measured modern inline-text-box vertical difference of approximately 0.60 mm temporarily and authorized merging this research PR. Follow-up [issue #32](https://github.com/NuaForma/NuaForma/issues/32) tracks diagnosis and correction. This acceptance is limited to the observed text-box difference: it does not establish a universal rendering tolerance, approve unknown template profiles or waive source preservation, barcode scans, other fidelity checks or process isolation. The research evidence and the limitation can be merged without claiming a production provider exists.

After accepting LibreOffice's additional redistribution obligations and pausing to evaluate Euro-Office, the user explicitly selected LibreOffice on 2026-10-12, authorized merging research PR #33 and resumed issue #11. The approved direction reuses DOCX generation and applies the measured native-shape compatibility mapping only to a temporary PDF conversion copy. Missing paragraph defaults may be supplied only through the approved explicit, caller-selected compatibility option; existing settings remain leading. The modern inline-text-box difference tracked in #32 remains temporarily accepted. Follow the [distribution checklist](libreoffice-licensing.md) for any bundled runtime. No production renderer has been implemented or added to the product modules; production isolation and the actual Linux package still require implementation and verification.

## Compared versions and method

- LibreOffice 26.8.1.1, build `bf6ef2662401c7d6dce671ab4deb26ee0af3a7c1`, Windows x86-64, headless conversion with a private profile per document.
- docx4j-export-fo 17.1.0, JAXB ReferenceImpl 17.1.0 and Apache FOP 2.11 on Java 17, with the XSL exporter and explicitly supplied font files. The visitor exporter was also run on the barcode and five-page watermark fixtures.
- Identical synthetic DOCX inputs for each primary renderer, recorded by SHA-256. Expected/generated pairs are built independently by the existing tests. Earlier Word renders are local interoperability references, not a production dependency or a guaranteed cross-renderer pixel baseline.
- Arial regular, bold, italic and bold italic were explicitly available to FOP from the local host for this private experiment; they are not redistributed or a Docker prerequisite. Libre Barcode 39 is the approved OFL-1.1 test font. A unique-family embedded-font control proves that the result does not merely come from the installed barcode family.
- Poppler rasterized all output at 100 DPI. pypdf 6.10.0 inspected PDF headers, geometry, extracted text and font descriptors; Pillow 12.3.0 and ZXing-C++ 3.1.1 independently decoded raster pages. All 95 pages were covered by visual review of their 48 distinct PNGs, with identical SHA-256 PNGs sharing the same review. This review identifies defects; it is not a passing fidelity certification.

All 28 primary conversions and both visitor probes produced readable PDFs with zero converter exit codes. This is specifically not evidence that every document was rendered correctly.

Both primary renderers retain two-page pagination for the round-trip, complex and ordinary barcode cases, one page for the isolated embedding controls, and five pages for each watermark case. All watermark variants retain their own renderer's page count and section sizes. That does not make Word and these renderers equivalent: the Word reference uses noticeably different paragraph spacing and text-box geometry.

The XSL and visitor comparisons agree on missing rotation and watermarks, so changing that exporter flag does not solve the blockers. The visitor's missing modern text-box content is an additional reason not to accept it as an automatic fallback.

## Conversion copy experiments

The follow-up used 28 one-page diagnostic conversions and a complete 14-document, 44-page conversion-copy matrix. Diagnostic pages were rendered at 150 DPI; the full matrix used the same 100 DPI as the original comparison. All 28 diagnostic pages were covered by visual inspection of their 17 distinct rasters; all 44 matrix pages were covered by inspecting the nine distinct changed rasters and checking unchanged/duplicate pages against the previously reviewed rasters. An additional one-page smoke conversion verified the final harness's before/after input-hash guard; it is not included in those counts.

The existing margin shape combines `rotation:90` with a `bottom-to-top` text flow. The dimensions-only experiment exchanges the explicitly supplied point width/height and changes the shape rotation to zero, retaining the text flow, native text, run properties and embedded font parts. It does not detect a barcode or change its encoding. All four barcode cases now independently decode as `NF001`, Code 39, orientation -90 degrees: expected, generated, embedded and unique-family embedded. Their inspected PDF fonts remain embedded, including the unique `NFTestFont639024` control. No glyphs were replaced with an image.

All 14 source DOCX SHA-256 values remain unchanged after conversion. In every temporary copy only `word/document.xml` changes; headers, footers, relationships, font metadata and embedded font bytes are preserved. Expected/generated pairs and the before/after round-trip pair remain raster-identical within LibreOffice. Fully transparent watermarks remain identical to the no-watermark control. Pagination and page geometry stay unchanged, and every pixel difference from the original LibreOffice comparison is confined to the first page's margin-text-box region. Watermarks remain visible with the same text, color, opacity and rotation on the same pages.

This dimensions-only route still loses the frame visible in Word and moves the barcode approximately 28 points (10 mm) horizontally and 4 points vertically compared with the independent Word reference. A readable vertical barcode does not excuse those layout differences. Adding explicit stroke attributes, adjusting a negative offset or setting text-anchor properties on the textbox does not restore the frame in that route. Switching to `v:rect` restores a border but the resulting full-page barcode fails decoding; thinning the stroke or adding the tested inset does not solve that. The hard-coded-position diagnostic is a counterexample, not a permissible conversion strategy.

An explicit rectangular VML shape-type definition is a more promising diagnostic: the normalized unique-font control has a visible frame and a vertical, full-page scanable barcode. However, its frame and text are still displaced from Word, and changing horizontal anchoring can move it into the body margin rather than reproduce the original position. The explicit-type approach has only been verified on that one synthetic control, not on the full matrix, arbitrary templates or inherited shape properties. It is not an implemented production compatibility layer.

The [upstream LibreOffice VML importer](https://github.com/LibreOffice/core/blob/master/oox/source/vml/vmlshapecontext.cxx) distinguishes text frames and shape-with-text-box paths. That supports investigating representation differences, but the experiment does not establish a general upstream fix or a universal mapping for Word shape geometry. A next compatibility implementation must model placement, frame properties, text orientation, inherited properties and supported combinations explicitly, then rerun the complete matrix against independent references. Do not ship the dimensions-only workaround as a silent fallback or select a backend on scanability alone.

Four research regression tests verify source-byte preservation, unchanged package parts and font resources, refusal to overwrite an existing copy, style-only transformation, idempotence and rejection of unsupported dimensions. The complete product build, architecture checks and publication metadata generation pass on Java 17; unchanged product test tasks reused their existing successful results. Product source, public APIs and the DOCX generation path were not modified. The draft research PR and issue #10 remain open.

## Native geometry follow-up

The next experiment replaces the measured VML margin-text-box representation with a native DrawingML rectangle in a private conversion copy. The rotated bounds come from the template's point dimensions; the horizontal anchor is the start of the section's right margin and the vertical anchor is the bottom of the text margins. Paragraphs, runs, font selections and embedded font parts remain native and unchanged. The default 0.75-point stroke follows [Office's documented VML interpretation](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/d019f23f-5977-43d8-b463-99ba8f6784eb). No barcode detection, raster replacement, fixture-specific page coordinates or global font installation is used.

This mapping is deliberately limited to the measured profile: explicit positive point dimensions, a type-202 shape with rotation 90, bottom-to-top text, zero insets, right alignment relative to the page, bottom alignment relative to margins, and a rotated width fitting every section's right margin. Matching unknown attributes, geometry or alignment is rejected. Wider-than-margin shapes, left/center/margin alignment and inherited/grouped shapes are not supported by this experimental mapping. The measured right-margin mapping is not a universal interpretation of every page-aligned Word object.

Six controlled cases vary the page width, right margin, shape width/height and ignored absolute offsets. Their native conversion copies all decode `NF001` vertically and reproduce Word's horizontal frame coordinate, including a wider page and a different right margin. The source's negative offsets are not arbitrary correction parameters: [Office ignores those offsets when the corresponding alignment property is set](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/d019f23f-5977-43d8-b463-99ba8f6784eb). The experiments measure that behavior rather than tuning a constant for the original fixture.

A clean full run converted all 14 documents and all 44 pages. Independent vector-frame and glyph-origin measurements against freshly rendered Word references give:

| Measured margin object | Largest horizontal difference | Largest vertical difference |
| --- | --- | --- |
| Frame edges, with the same 0.75-point stroke | 0 points | 0.95 points |
| Native text/barcode glyph origins | 0.94 points | 1.221 points |

The maximum measured glyph-axis difference is approximately 0.43 mm, compared with the earlier 10 mm horizontal displacement. These are observations, not a silently adopted product tolerance or a claim of pixel identity. All four barcode cases decode `NF001`, Code 39, orientation -90 degrees on full 100-DPI pages, with embedded fonts including the unique-family control. Expected/generated pairs and transparent/plain watermark pairs remain raster-identical. Page counts and page dimensions remain unchanged. All 14 original DOCX hashes remain unchanged; only `word/document.xml` changes in the margin-only conversion copies. The complete 44-page review reuses verified unchanged pages and checks all nine distinct changed first-page rasters. Fresh Word oracle rasters are pixel-identical to all 44 previously reviewed Word pages.

Earlier attempts are not counted as successful full runs: the first DrawingML matrix exposed a missing namespace on unprocessed input fixtures, fixed with explicit local DrawingML namespace declarations and XML validation. A subsequent run hit the owned-process 100-second deadline on the isolated font case; it was stopped, retained as a failure and rerun in a fresh directory. The clean full run completed without that timeout. This does not establish production process reliability or the cause of the timeout.

An additional inline-text-box experiment restores the ordinary VML frame, but reveals overlap with the following modern box when the source lacks paragraph defaults. That is still a failing layout, not an accepted fallback. Word's private canonical serialization supplies a missing paragraph-default block with 8-point after-spacing and automatic line spacing 278/240 on this workstation. A separate diagnostic, materializing only that observed block in two private copies, removes the overlap and reproduces the ordinary frame's exact coordinates and dimensions in the round-trip control. The existing modern frame still differs vertically by 1.69 points. All four diagnostic pages were visually inspected. This isolates a style-default interpretation issue; it does not prove those observed defaults are universal or justify copying workstation preferences into production.

Nine research unit tests now cover the old dimensions experiment and native-copy isolation, content/font preservation, dynamic dimensions, unique drawing IDs, namespace-valid package XML, idempotence, refusal to overwrite and rejection of unmeasured matching profiles. The product build and publication metadata generation still pass on Java 17 with cached, unchanged product test results. Product APIs, dependencies and returned DOCX generation remain unchanged.

**Disposition of this earlier experiment:** the following explicit option resolves the missing-default policy and ordinary-frame overlap in the measured matrix. The remaining modern-frame difference is now temporarily accepted and tracked in #32. General OOXML/inherited-property coverage, backend selection and production isolation remain implementation work. The diagnostic Word-default materialization must never become an implicit runtime dependency or silent template rewrite.

## Explicit compatibility option follow-up

The user approved an explicitly configurable missing-paragraph-default policy for an isolated PDF conversion copy. The agreement is recorded in [ARCHITECTURE.md](../ARCHITECTURE.md). The research helper accepts two caller-selected values and never invokes Word or reads workstation preferences. Omission preserves `styles.xml` byte-for-byte. Existing template defaults, alternative after-spacing modes, explicit line values/rules and individual style/paragraph overrides remain leading. No returned DOCX, public contract, product dependency or production processing path changes.

The full opt-in run explicitly selected 8-point after-spacing and automatic line spacing 278/240. These values reproduce the observed Word settings for this synthetic matrix; they are not universal Word defaults. Only `word/document.xml` and missing properties in `word/styles.xml` change in these private copies. Font resources, headers, watermarks and all other package parts remain unchanged. All 14 originals retain their source hashes.

All 14 PDFs and 44 pages converted successfully. Every page was covered by visual review of 32 pixel-distinct full-page rasters and verified duplicates. No ordinary/modern text-box overlap remains. Independent vector measurements show the ordinary 260-by-35-point frame matches Word exactly in all 12 documents containing it; the modern 360-by-36-point frame has unchanged width, height and horizontal placement but remains 1.69–1.70 points higher than Word (approximately 0.60 mm). This is a remaining fidelity difference, not a silently accepted tolerance. The margin-frame and glyph-axis differences remain within the previously measured ranges. All four full-page barcode cases independently decode `NF001`, Code 39, orientation -90 degrees, including the isolated unique-family font case. Page counts and sizes are unchanged; expected/generated and transparent/plain pairs remain raster-identical. The requested watermark variants remain visible with their respective rotation, color and opacity; deliberately opaque watermarks can obscure underlying text as requested.

Seventeen fresh research tests pass, covering opt-in behavior, default omission, preservation of explicit/alternative spacing, invalid values, idempotence and unchanged source/font parts, in addition to the earlier geometry/isolation cases. The full product build, architecture checks and publication metadata generation pass on Java 17 with unchanged product tests reused. The helper and its XML profile remain research-only, not a production upload normalizer.

**Accepted research limitation:** the user temporarily accepted the modern inline-frame difference and authorized merging PR #31; #32 remains open to establish its cause and fix. Broader inherited/grouped OOXML profiles remain unqualified. Backend selection and production isolation are outstanding, so research merge does not make PDF output or this option available to engine consumers.

## Euro-Office alternative evaluation

At the user's request, the LibreOffice implementation path was paused and the same trusted fixtures were tested with Euro-Office's direct `x2t` converter. The [official converter interface](https://github.com/Euro-Office/core/blob/5a33ce6c4a63387e8576c7e763b70cd971988b24/X2tConverter/README.md) accepts a conversion XML file; this experiment starts no editor, database, message broker or web server. It is not a production API or a claim about the editor's full service workflow.

The documented official `latest` image resolved to Linux/amd64 digest `sha256:beca380debb9b4eadb7e4c662d112a325c5df0f2179453a4affd8e6ba5d00562`, but its installed package reports `9.3.4-hotfix.1`. The latest [official package release is 9.3.5](https://github.com/Euro-Office/DocumentServer/releases/tag/v9.3.5). The 9.3.5 Debian archive was therefore fetched separately, checked against the release asset's SHA-256 `2c14ce8eabcf58bd4d6e56ca7304d565de48e6867f4bbd31ef41a9bacfcbaa13`, and extracted without installing it or running package installation scripts. Its complete `/var/www/euro-office` tree was mounted read-only over that subtree in the original image for the 9.3.5 conversion tests. This is a pinned package-overlay experiment, not verification of an official 9.3.5 Docker image or a complete deployment. Both converters print internal version `2.5.565.0`, so that banner alone cannot identify the package release. The 9.3.5 converter binary SHA-256 is `3315bbbb1555588981719846a9590a2b9afb69f4ffdefcc5004fb262af79e163`.

Each version converted two complete 14-document / 44-page matrices: unchanged original DOCX and the exact previously measured native DrawingML copies with explicit 8-point/278-unit paragraph defaults. No new LibreOffice conversions were run. All 56 matrix PDFs / 176 pages were covered by visual review of 52 globally pixel-distinct full-page rasters and verified duplicates. The 9.3.5 raw/native rasters are pixel-identical to the corresponding 9.3.4-hotfix.1 rasters on every page. Initial smoke checks and a final-code hash-guarded smoke are additional diagnostics, not counted as matrix documents. The final-code smoke's two page rasters match the fully reviewed raw run exactly.

| Check | Unchanged DOCX | Native DrawingML / explicit-default copy |
| --- | --- | --- |
| Modern inline frame versus Word | Large upstream-flow differences remain when missing defaults and legacy boxes are not normalized | Still 1.737–1.743 points higher, approximately 0.613–0.615 mm: the originally investigated small difference is not removed |
| Ordinary text-box frame | The expected legacy VML border is absent | Frame bounds are within 0.011 points of Word in the measured cases |
| Margin frame and placement | Expected VML frame is absent; barcode is displaced toward the page edge | Frame appears but its height changes: the round-trip control shrinks from 120 to 44.060 points; the barcode control from 180 to 100.830 points |
| Font-based barcode | Three cases decode `NF001` vertically at both 100 and 300 DPI when the family is explicitly present in the private font cache | None of the four full-page cases decode at either 100 or 300 DPI; visible native-font bars do not constitute a passing scan |
| Unique-family font embedded only in DOCX | PDF uses embedded Arial instead of the unique font; no barcode decode | Same fallback and failed decode |
| Requested watermark variants | Diagonal/vertical text becomes small colored lines rather than the requested text; opaque horizontal output is pixel-identical to no watermark | Same watermark failures; the compatibility copy does not touch the header watermark objects |
| Pagination, source preservation and paired results | All original hashes, page counts/sizes and expected/generated parity are preserved | Same checks pass; conversion inputs and originals remain unchanged |

These are fixture-specific observations, not a claim that Euro-Office cannot render other documents or that no workaround exists. Full-page ZXing-C++ decoding uses the same approved decoder as the earlier evaluation, without cropping or treating a partial barcode as sufficient. Arial faces and Libre Barcode 39 are supplied privately for this QA experiment; the unique-family control deliberately has no installed/supplied family outside its DOCX embedding. No host fonts are installed or redistributed.

Conversion containers run as UID/GID 1000, with network disabled, no published ports, a read-only root, dropped capabilities, no new privileges, bounded CPU/memory/process count and private writable output/tmp areas. Inputs, font resources and package overlay are read-only. Only synthetic copies and selected QA fonts are mounted, never the repository, user home or Docker socket. Deadline cleanup verifies an owned UUID label before removing a timed-out conversion container. This local harness is not a production sandbox certification, and the larger worker/distribution policies still need implementation.

The first attempt to extract the 9.3.5 archive into a Windows bind mount ended nonzero because tar could not restore the mount-root mode/timestamp. It is retained as a failed diagnostic and was not used for conversions. A fresh, labeled Linux Docker volume extraction completed successfully; only the checksum-verified package subtree is mounted into the runtime. The image, package archive, failed extraction, private QA fonts and successful package volume remain local research data. Conversion containers are removed on completion; no persistent Euro-Office service is left running.

Euro-Office publishes its [core under AGPLv3](https://github.com/Euro-Office/core/blob/main/LICENSE.txt); its [licensing guide](https://euro-office.github.io/documentation/introduction/licensing/) also identifies inherited ONLYOFFICE licensing and lists third-party/binary audit documentation as work in progress. A new AGPL integration requires its own approval and review of the exact code/process boundary, distribution and any modified network-accessible version; merely using HTTP or a separate process is not a universal exemption. No AGPL source, binary, Docker image or font asset is added to NuaForma's production artifacts. The [upstream core repository](https://github.com/Euro-Office/core) has recent development activity and the 9.3.5 release is recent, but maintenance activity does not qualify rendering fidelity or establish a completed license/security audit.

Twenty-one fresh research unit tests pass, including the direct-converter containment flags, read-only scoped package mount and ownership-checked timeout cleanup. Real conversions and independent visual/font/scan checks are separate evidence, not mocked renderer results. The complete Java 17 product build, architecture checks and publication metadata generation pass with cached, unchanged product tests. The returned DOCX path, product APIs and Maven dependencies remain unchanged.

**Recommendation and subsequent decision:** do not switch to this Euro-Office route as the first production backend on the evidence above. It retains the small inline-frame difference and adds unqualified watermark, margin-frame and embedded-font behavior on our fixtures. The user subsequently selected LibreOffice and resumed #11; #32 remains open. Euro-Office is not adopted, and no further Euro-Office implementation or investigation is in scope.

## Resources, isolation and Docker feasibility

Each primary conversion started a fresh process/profile. Recorded elapsed time was 9.530–11.785 seconds for LibreOffice and 8.303–12.597 seconds for FOP. FOP's process peak RSS was 281,668–306,944 KiB with a 512 MiB heap ceiling. The research launcher and all its runtime JARs occupy about 35.1 MB. LibreOffice peak process-tree memory was not measured. These are single-machine cold-process observations with fonts present, not throughput benchmarks, service limits or a fair cross-platform speed ranking.

FOP can run headlessly on Java 17 in Linux. LibreOffice offers a headless executable for Linux; neither requires Word, a cloud account or a commercial conversion service. A Linux container is feasible in principle, but this Windows LibreOffice versus Linux/JVM comparison does not verify Linux font lookup, LibreOffice packaging, startup cost or pixel parity. No Docker image has been built or claimed as working. Pin the selected renderer and image, preserve notices, then reproduce the cases inside the actual image before advertising Docker support.

Production conversion needs a non-root bounded worker, a private writable temporary area and font cache, explicit font resources, network denial, filesystem access restrictions, macro/active-content rejection, queue/concurrency bounds, output caps and cancellation/deadline enforcement with owned-process cleanup. For FOP, global font maps and caches must not cross tenants; an in-process Java library is not automatically request-isolated. For LibreOffice, `--headless` and a private profile are not a sandbox. The research harness's timeout and heap limit do not establish these production controls.

## PDF versions and profiles

Observed defaults are PDF 1.7 for LibreOffice and PDF 1.4 for FOP. The inspected fonts in these fixtures have embedded font streams, including the unique-family barcode control. This proves fixture-specific embedding, not universal font handling or permission enforcement by a future PDF provider.

LibreOffice documents [version/profile export switches](https://help.libreoffice.org/latest/en-US/text/shared/guide/pdf_params.html), including PDF version selection and archival/accessibility options. FOP documents [PDF/A settings](https://xmlgraphics.apache.org/fop/2.11/pdfa.html). Those are upstream options, not NuaForma capabilities: no PDF/A or PDF/UA validator was run, no empty signature-field workflow was tested and no profile is advertised. A future provider must describe and validate supported combinations and reject unverified/unsupported requests instead of guessing from a PDF header.
