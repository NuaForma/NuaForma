# Container release procedure

The separate development target is intended for `ghcr.io/nuaforma/nuaforma-playground:<same-version>`, with its own native AMD64/ARM64 qualification and matching source/license audit. Production and Playground retain distinct OCI indexes; do not add its JAR/assets to the normal image. The native candidate workflow builds/tests both without uploading binaries. The existing public release procedures publish only their explicitly selected/audited artifacts; the Playground is not implicitly published by implementing its target. Before authorizing a Playground release, prepare its own matching archives, truthful SBOM, notices/sources, startup/GUI warnings and aligned website/download instructions. No existing alpha tag/image is replaced.

Source container targets generate a static CycloneDX 1.7 inventory from the assembled runtime; qualify its actual `/api/v1/sbom` bytes and validate them against the official schema on both architectures. This supplements rather than replaces the source/license/security gate. See [SBOM scope](sbom.md).

Target registry: `ghcr.io/nuaforma/nuaforma`, linked to this repository. GitHub Pages can serve documentation/download links; it is not a container registry. Public GHCR images can be pulled anonymously, so on-premise generation needs no GitHub account. Registry access is needed only to obtain/update an image, not to generate documents afterward. See [GitHub's Container registry guide](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

The manually dispatched **Prepare container release** workflow builds Java 17 libraries and the Java 25 service, then qualifies native AMD64/ARM64 candidates and exports exact package/JAR/JVM inventories and qualification metadata. Validator child JVMs deliberately remain pinned to Java 17; see [runtime compatibility](java-runtime-compatibility.md). It runs only against `main`, uses pinned actions and a read-only repository token, and has no registry login, package-write permission, image upload or release creation. The normal required `Build (Java 17)` check stays unchanged. A hosted runner that cannot provide the agreed isolation must fail qualification, not disable host protections. The local qualification commands in the [service guide](../deployment/pdf-runtime/SERVICE.md) remain usable independently.

This preparation intentionally stops before publication. Redistributing a supposedly private downloadable image or workflow artifact can already trigger third-party license obligations; withholding a public `latest` tag does not waive them. Until the distribution audit is complete, only non-executable inventory/check metadata is uploaded. No first version, release tag or public image is created by this milestone.

The service includes [operator font and extension mounts](../deployment/pdf-runtime/MOUNTS.md), implemented under [issue #35](https://github.com/NuaForma/NuaForma/issues/35). Qualify these boundaries again on every final release candidate; completing #14/#35 or their preparation checks does not authorize publication or fulfill the candidate-specific license/source audit. Operator-provided files are not image build inputs and must not be uploaded as release assets.

## Mandatory website synchronization

Every release, including prereleases, library-only and container-only releases, must be followed by an explicitly verified update of `nuaforma.dev`. Keep container and Maven library versions distinct when only one changes. Preparing local files or changing the dynamic release banner alone does not complete this step.

- Update the fallback release banner, release notes/links, applicable dependency snippets and repository README to match the published artifacts. Change only the versions actually released.
- For container releases, update both AMD64/ARM64 Compose kits, Dockerfile examples, Helm image digest/chart metadata and their source/license links. Rebuild the downloadable deployment ZIPs and check them against their source files; retain the reviewed security settings.
- Review the example template, JSON scenarios, Bruno/Postman collections and endpoint/capability descriptions against the release. Regenerate and render examples when their content or layout changes; never advertise planned features as available. Rebuild the client/test ZIPs and complete starter kit after updating their sources, and check the complete kit's deployment and collection folders against the individual downloads.
- Pass the applicable site, JavaScript, Compose and document-example checks. Publish through the normal protected PR/Pages workflow only under the maintainer's deployment authorization, after the advertised artifacts are available.
- Verify the public HTTPS page and applicable direct downloads, including archive checksums, current version/platform selection and absence of stale artifact references. Do not report the release workflow complete while this website follow-up remains outstanding; report a deployment blocker explicitly.

## Release gate

For future releases, Linux/amd64 and Linux/arm64 are both required variants under one versioned OCI image index. The preparation matrix runs on native runners and retains separate per-architecture metadata. Both variants must pass the same fidelity/isolation/security and exact-source/license gates before publication; compilation under QEMU is not qualification. The historical alpha publisher and approval record stay immutable and amd64-only. See [the ARM64 candidate guide](../deployment/pdf-runtime/ARM64.md); native Apple Silicon/Podman validation remains a separate compatibility obligation.

The manually dispatched **Publish audited multi-platform container** workflow is prepared for new versions, not for republishing the alpha. It requires the existing protected `ghcr-release` environment, a verified annotated source tag and `release-approvals/<version>.json` containing exactly `amd64` and `arm64` under `platforms`. Each entry records native qualification architecture, independent audit/fidelity/security approvals, archive/config SHA-256 and anonymously accessible matching `sourceMaterials`; shared fields bind version, source commit, maintainer and stable/prerelease `latest` policy. No approval record is created automatically.

The publisher consumes already audited `nuaforma-container-<version>-<architecture>.tar.gz` release assets, never builds at publication. Export each audited image using its local tag `nuaforma:<version>-<architecture>-archive`. Both archives must pass identity/configuration/source-label checks before registry authentication. The workflow refuses existing version/architecture tags, publishes immutable platform tags and then their combined version index, and verifies its two child manifest digests against the reviewed configuration identities. Stable versions update `latest` to the same two-platform selection; prereleases do not. An interrupted network push can leave one approved architecture tag without a complete index: recover explicitly rather than overwrite immutable tags or claim the release complete. Merely merging this preparation does not approve a release or fulfill either platform's distribution gate.

For the exact final candidate, a maintainer must complete the [distribution checklist](libreoffice-licensing.md), not merely acknowledge it:

The development Markdown sweep on 2026-10-12 updated current capabilities, examples and historical-research boundaries, including the root README. Before the first publication, recheck documentation against the exact candidate and selected version, replacing source-build-only instructions with verified download instructions only after availability is established. This maintainer-required documentation gate is separate from the exact-image license/source and fidelity checks below.

1. Record the source commit, Java/platform/build inputs, component inventory, actual binary/source versions and checksums. Include all OS packages, renderer components, Java legal materials, original application/validator dependency JAR notices, fonts and Bubblewrap build materials. Keep the image's upstream copyright/license records and notices extractable without starting the service.
   For the split-runtime service, review both Java 17 validators and Java 25 server, retain both exact OpenJDK sources/legal trees and build provenance, and record `javaRuntimeFilesSha256` for each platform's `java-sha256.txt`. A historical single-JVM approval cannot cover the new runtime layout; the pre-transfer source gate rejects missing or different JVM inventories.
2. Map every inventoried component to its applicable terms, retained notices and source obligations. Collect and archive the exact corresponding source, patches and build materials for every component that requires them. Upstream links and an inventory alone do not establish compliance. Bubblewrap's source is retained in the image; the rest still needs a completed, candidate-specific source provision review.
3. Provide recipient-accessible matching source materials and instructions alongside the versioned release, with checksums. Verify anonymous retrieval before making the binary available. Use immutable assets; split archives if necessary to satisfy hosting limits. Never include private interoperability fonts, user documents, credentials or local agreements.
4. Repeat actual isolated HTTP generation, missing-converter, cancellation/shutdown, font embedding and independent visual/barcode checks on the final candidate. A successful candidate build is not a substitute for the final image's legal or fidelity review. Record vulnerability findings and their disposition against the pinned OS/JVM/JAR inputs; do not present absence of known matches as a security guarantee.
5. Keep the reviewed record bound to the source commit, exact component/JAR checksums and final image digest. Reopen the gate after any changed component, base image, font, build input or release version. Inventory artifacts expire; archive accepted records and source provision durably with the release.

NuaForma's independently written code remains Apache-2.0; the combined image is not wholly Apache-2.0. Applicable third-party licenses remain in force. In particular, distributing MPL-covered executables requires making their corresponding source available and informing recipients how to obtain it; see [MPL-2.0 section 3.2](https://www.mozilla.org/en-US/MPL/2.0/). Apply other component terms independently.

## First publication setup

The selected first candidate is `0.1.0-alpha.1`, using the same release version as the five libraries. The immutable source anchor will be `v0.1.0-alpha.1` after candidate preparation passes; no tag or release is created by this document. Stable releases publish both their immutable version tag and the moving `latest` alias to the same approved image; prereleases never update `latest`. Pin a version or digest in production. The next development version is selected deliberately according to the actual changes, not automatically advanced to the next minor.

The separate **Publish audited alpha container** workflow is prepared and protected by `ghcr-release`. It requires an annotated, verified release tag and a complete exact-candidate review record; missing evidence blocks publication before registry authentication. It imports the already qualified Docker archive and verifies its checksum, loaded root filesystem, runtime configuration and source/version identity instead of rebuilding or repeating container-generation tests. The maintainer approved reusing the completed exact-candidate qualification for publication; this does not waive initial qualification or permit substituting a different image. The agreed direction is a manually started release, never an automatic push from `main`:

- Publish the approved candidate to GHCR using the workflow's narrowly scoped `GITHUB_TOKEN` with `contents: read` and `packages: write`, rather than a stored personal access token. Separate any release-asset creation permission from the image push. See [GitHub's publishing guide](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images).
- Require a protected release environment and explicit maintainer approval after the candidate-specific legal/fidelity review. Configure and verify the environment before adding an active publishing job; a YAML environment name alone does not establish required approval.
- Select the first prerelease number explicitly (for example, a future `0.1.0-alpha.1`, not a version already released). Keep module/distribution metadata consistent with the selected version. Publish exact version tags and the final digest; never overwrite an existing version tag. Do not point `latest` at prereleases. Moving stable aliases require an explicit release policy.
- Link the package to `NuaForma/NuaForma`; verify organization package permissions. New GHCR packages are private by default. A maintainer must explicitly set public visibility after the distribution gate; repository visibility alone is not enough. Verify anonymous pull by version and digest and independently check the downloaded artifact/inventories.
- Make the matching license/source/checksum materials available before the binary, and document the download command plus supported platform. Do not advertise ARM64 until qualified. Provide offline transfer via an audited `docker save` artifact if requested; offline artifacts carry the same obligations.

The `ghcr-release` environment has been configured with maintainer review, no administrator bypass and exact-main-only access. No package or image has been published and no package visibility, domain/DNS setting or public service deployment has been changed. The maintainer authorized the first alpha publication only after all release conditions pass. Separately publishable engine JARs use their own Maven release procedure; GHCR publishes containers, not Java artifacts.

## Retained materials and reproducible preparation

The offline/review tools under `tools/container` collect exact source and notice inputs, bind them to the actual image inventory and package allowlisted source archives. They do not upload assets or approve their own collection. `review_package_materials.py` resolves Debian package-documentation symlinks inside the retained archives, not through the host filesystem. `collect_application_materials.py` binds runtime JAR bytes to their resolved coordinates and retains original embedded notices, inherited POM licensing and matching source JARs. `prepare_application_materials.py` stages those materials into the production distribution before Docker builds, supplementing original docx4j notices and ANTLR 2 terms where binary JAR metadata is incomplete.

`package_source_materials.py` creates the four archives described in [SOURCES.md](../deployment/pdf-runtime/SOURCES.md), with per-input and archive SHA-256 manifests. It excludes the unused Windows bootstrap binary and selects only explicitly collected materials, never a checkout, QA font directory or arbitrary build tree. Publish and anonymously verify these source assets before any image/archive distribution. Their presence on local disk does not establish recipient access or approve a different final image.
