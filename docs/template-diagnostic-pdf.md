# Marked template diagnostic PDF

This development-only operation locates a parser error in a private template, starting with the selected `0.3.0-alpha.4` release (#150). Consult the actual signed release for public availability; published alpha.3 does not include it. Normal generation still fails; the diagnostic PDF is a separate artifact, not a generated business document or archival export.

After a syntax failure, choose **Download diagnostic PDF** in the Playground. The browser resends the original failed request, template and resources, even after builder edits. A request-private copy preserves literal template content, adds a red `[ERROR 1]` marker and appends an explanation page with the reason, part, paragraph, local position and bounded excerpt/caret. Known secret-field excerpts remain redacted. The document itself contains original template text: protect development instances and downloaded files.

Only the first locatable error is marked. Mapping uses actual Word objects, not text search. Structural block errors mark the opening paragraph. Mixed object/text runs are colored with a label at the failed text position. Adding the label can change wrapping; this is a navigation aid. Automatic wrapping does not split expressions; manual breaks and Word objects can introduce separate fragments.

`POST /api/v1/diagnostics/template` accepts the ordinary bounded multipart request/template/resource parts. It exists only in trusted startup development mode; production returns 404 and requests cannot enable it. A successful diagnostic operation returns independently validated standard PDF with filename `template-diagnostic.pdf`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Request-ID` and `NuaForma-Diagnostic-Artifact: template-error`. The original output profile and requested watermark do not apply to this separate diagnostic artifact. Caller font declarations/resources still apply.

Contract 0.6 adds optional `TemplateDiagnosticProvider.diagnoseTemplate(request, output, context)`. Native PDF implements it with an explicit development-context requirement. Original provider interfaces/constructors remain unchanged; older runtimes reject new built-in providers before initialization. `DocxProvider.diagnosticCopy` prepares the marked DOCX. No new artifact or production dependency is introduced.

Package checks, native profile restrictions, font policy, admission, byte/work limits, cancellation and mandatory structural validation remain enabled. There is no Office fallback, external retrieval, second evaluator, server-side artifact cache or partial success output. Unsupported source layouts/fonts can prevent PDF creation. The Playground retains the original error and reports why the PDF is unavailable; it does not substitute a text-only PDF. Valid templates and errors without a reliable source mapping produce no diagnostic artifact.

Source fix #154 excludes Word hidden text from syntax activation and omits it from the private PDF intermediary. Only a visible parser error can create the diagnostic; a template with only hidden errors is valid for syntax inspection and does not produce a diagnostic PDF. See the DOCX visibility rules for inherited styles, overrides and unsupported conditional table visibility. This does not establish the cause or resolution of an unrelated DOCX serialization failure.
