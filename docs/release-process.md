# Release with one final approval

**Publication policy:** stable releases go to Maven Central; alphas and other immutable prereleases go to Nexus. Snapshots publish automatically after each green develop push, with manual dispatch also available. See [Nexus setup, snapshots, integrity and consumer configuration](nexus-publishing.md). The existing one final `release` approval still covers immutable releases and the matching site.

This is the normal release procedure from `0.3.0-alpha.2`, approved by the maintainer on 2026-10-27. It supersedes the repeated preparation, exact-container qualification and separate upload/publication approvals described by the legacy Maven/container recovery guides. Existing CI remains mandatory; this changes release orchestration, not product quality gates or license obligations.

## Prepare once

1. Merge the reviewed product/version changes into develop, then promote develop to main through a normal PR. Wait for the exact main commit's Java 17/25 checks and actual SonarCloud analysis. Create a verified signed annotated `v<version>` tag at that commit.
2. Dispatch **Release with one final approval** on main with the version, a successful native-container CI run and a published source-review baseline. The workflow verifies the tag/source/version and exact current JVM/Sonar checks. Native CI may be reused only if every runtime, dependency, build, container, qualification and fixture input is unchanged; only the release version property is normalized. Runtime changes require a fresh successful native CI run on both AMD64 and ARM64.
3. Build/sign the six libraries and both application distributions once. Verify the 24 artifact signatures, POMs, Java 17 baseline and bundle identity. CI has already exercised the independent consumers and complete test suite; release preparation does not run them again.
4. Build each of the four native images once from those same JVM distributions. Check platform, non-root configuration, source/version labels and actual third-party inventories. Do not repeat endpoint, example, visual, load or consumer qualification during the release. An inventory mismatch stops preparation for a new source/license review; it is never silently accepted.
5. Matching source archives may belong to an earlier immutable release when the exact package/JAR/both-JVM inventories still match its review. Retrieve and hash all three public source archives before transferring binaries, retain original notices/legal files, and generate the in-image source notice pointing to that exact baseline. The candidate manifest records this reuse explicitly. It does not claim those old binaries qualify new application behavior.

The workflow artifacts contain the signed Maven-layout bundle, shared runtime inputs, four native image archives and their inventories, and a candidate manifest with all hashes and CI identities. They are build preparation, not public release coordinates. Signing uses existing repository-accessible organization secrets in the signing step only; preparation has no Central upload credentials or registry write permission.

## One final approval

Only the `publish` job uses the protected **release** environment: reviewer `mrhoeve`, main only, no administrator bypass, self-review allowed for the sole maintainer. Its pending deployment is the single final approval for Maven, both container indexes, GitHub release and the matching website. Review the complete candidate and its runtime/security exception together. Exceptions from an older release do not transfer automatically; approving this candidate explicitly accepts the exception written in its manifest for this evaluation alpha.

After approval, rehash the same artifacts, check loaded image configuration identities and refuse existing immutable versions. Stable `X.Y.Z` versions upload once to Central in USER_MANAGED mode, wait for validation, independently match all 24 staged bytes, and request publication once. Prereleases instead publish the exact approved signed bundle directly to Nexus; the reviewed candidate binds the destination URL and verifies all uploaded files anonymously. Only the selected destination credentials are loaded. Push the exact loaded images and verify both architecture/config identities in each version index. Prereleases leave `latest` unchanged. Anonymous retrieval of the 24 Maven artifacts must match the approved bytes before reporting success. No build or full test suite runs after approval.

The website is a separate repository. Prepare its version/download changes in advance, bind the actual published digests and signed product source after publication, run static/package checks, and promote its checked PR to main under the same release authorization. Its main-only Pages deployment adds no approval. Do not create a cross-repository write token merely for orchestration. Preserve document fixtures and image-comparison content; do not regenerate Word examples for a version bump. Verify the live version and download hashes before closing the release issue.

## Failure and recovery

Upload and publish requests are never automatically retried. Read-only Central validation/propagation checks may repeat. Publication receipts are retained even if a later step fails; inspect the actual Portal deployment UUID, registry tags and GitHub release state first. Do not rerun the complete workflow after an upload or push has started: an interruption may have succeeded remotely. Resume only the missing, already-approved operation using the recorded candidate bytes; never rebuild or overwrite version tags. A new candidate or a different version needs a new final review.

The older `maven-central` and `ghcr-release` environments and workflows remain protected for deliberate recovery of releases using their old review records. They are not the normal path for new releases and must not be dispatched alongside the unified workflow. Legacy Central mutation entry points now accept stable versions only; fixed historical alpha mutation workflows stop before building or loading credentials. Read-only historical verification remains available. Organization secrets remain scoped to the selected repositories; no secret values belong in release artifacts or receipts.
